> 목적: 현재 채점 로직의 완성도 평가 및 보완 방향 제시

## 1. 전체 완성도 요약

인프라(수집·샘플링·에러 처리)는 학부 캡스톤 기준으로 상위권.
약점은 채점 기준값과 배점 균형에 집중되어 있음.

| 항목 | 완성도 | 비고 |
|---|---|---|
| 데이터 수집 (API, 비동기, Rate Limit) | ⭐⭐⭐⭐⭐ | 손댈 필요 없음 |
| 안티 치팅 (fork, SHA dedup, 오너십) | ⭐⭐⭐⭐ | 충분 |
| 커밋 샘플링 | ⭐⭐⭐⭐ | 균등 샘플링 양호 |
| Contribution 점수 | ⭐⭐ | 만점 기준 너무 낮아 변별력 부족 |
| Quality 점수 | ⭐⭐ | duration 편중으로 CI/CD·테스트 무력화 |
| Consistency 점수 | ⭐⭐ | 상수 임의, 샘플링 편향, 배점 미미 |
| 집계 방식 | ⭐⭐⭐ | LOC 가중 평균 합리적. 엣지 케이스 존재 |

## 2. Contribution (최대 60점)

### 현재 로직

```python
loc_score    = min(100, valid_loc / 1500 * 100)      # 만점: 1,500 LOC
commit_score = min(100, analyzed_count / 50 * 100)   # 만점: 50커밋
blend        = loc_score * 0.7 + commit_score * 0.3
contribution = (blend / 100) * 60
```

### 문제 1: 만점 기준이 너무 낮아서 변별력이 없다

LOC 1,500줄이면 만점. 학부 프로젝트 하나만 제대로 해도 쉽게 넘는 양.
레포 2~3개 스캔하면 거의 모든 지원자가 contribution 만점 근처를 받게 됨.
**60점 배점의 변별력이 사실상 0.**

커밋 50개도 마찬가지. 균등 샘플링 최대 75개를 뽑는데, 조금만 활발한 레포라면 분석 성공 커밋이 50개를 쉽게 넘음.

### 문제 2: LOC가 "유효 코드"를 정확히 반영하지 않는다

`valid_loc`은 `additions`만 합산. 파일 삭제 후 재작성 시 additions가 두 번 잡힘.
리팩토링을 많이 할수록 LOC가 부풀려지는 역설 발생.

### 보완 방향

**로그 스케일 적용으로 변별력 확보:**

```python
# 예시: 로그 스케일 LOC 점수
import math
loc_score = min(100, math.log(valid_loc / 100 + 1) / math.log(100) * 100)
```

초반 증가는 빠르고 후반은 완만해져서, 1,500줄이든 15,000줄이든 변별력 유지.

**또는 진단 체크리스트로 전환:**
Plan3에서 점수와 연봉을 분리했으므로, contribution을 정밀한 숫자로 다듬기보다 "코드량: 충분/보통/부족" 같은 정성적 표현으로 전환하는 것도 방법.

## 3. Quality (최대 30점)

### 현재 배점 구조

```
CI/CD 실질성:  최대  5점  (blob size > 200B)
테스트 비율:   최대 25점  (5% 미만 0점 / 5~20% 15점 / 20% 이상 25점)
유지보수 기간: 최대 30점  (7일 미만 0점 / 7~30일 15점 / 30일 이상 30점)

합산 후 min(30)으로 캡
```

### 문제 1: duration이 quality를 지배한다

`pushed_at - created_at > 30일`이면 30점. 레포를 만들고 한 달 뒤에 커밋 하나만 올려도 30점.
실제로 30일간 유지보수한 것과 한 달 방치 후 한 번 푸시한 것을 구별하지 못함.

### 문제 2: CI/CD와 테스트가 무력화된다

합산 상한이 30인데 duration만으로 30점을 채울 수 있음.
**CI/CD와 테스트를 아무리 잘 갖춰도 점수에 영향이 없는 경우 발생:**

```
사례 A: duration 30 + CI/CD 0 + 테스트 0 = 60 → min(30) = 30점
사례 B: duration 30 + CI/CD 5 + 테스트 25 = 60 → min(30) = 30점
→ A와 B의 quality 점수가 동일
```

### 보완 방향

**방향 1: duration 기준 강화**

단순 기간이 아니라 "기간 중 실제 커밋이 있는 주(week) 수"를 사용:

```python
# 예시: 활성 주 수 기반 duration
active_weeks = count_weeks_with_commits(commit_timestamps)
if active_weeks >= 8:
    duration_pts = 10.0
elif active_weeks >= 4:
    duration_pts = 5.0
else:
    duration_pts = 0.0
```

이렇게 하면 방치 레포가 걸러짐.

**방향 2: 캡 제거 + 배점 균등 분배**

```
CI/CD:      최대 10점
테스트 비율: 최대 10점
유지보수:    최대 10점
합계:       최대 30점 (캡 불필요)
```

세 항목이 모두 변별력을 가지게 됨.

## 4. Consistency (최대 10점)

### 현재 로직

```python
consistency = max(0.0, 10.0 - std * 0.5)
# std = 커밋 간격(일)의 모표준편차
# 커밋 < 5개면 0점
```

### 문제 1: 상수 0.5의 근거가 없다

std 20일이면 0점인데, 개인 프로젝트에서 커밋 간격 표준편차 20일은 흔함.
주중에 몰아서 커밋하고 주말에 쉬는 패턴만으로도 std가 상당히 올라감.

### 문제 2: 샘플링이 인위적 갭을 만든다

균등 샘플링으로 초기/중간/최근에서 뽑으면, 실제 커밋 패턴과 다른 간격이 생김.

```
예: 200개 커밋, 초기 25 + 중간 25 + 최근 25 추출
    → "초기 마지막 커밋 → 중간 첫 커밋" 사이에 인위적 대형 갭 발생
    → std 상승 → 일관성 점수 하락
```

실제로는 꾸준히 커밋했더라도 샘플링으로 인해 점수가 깎이는 구조.

### 문제 3: 10점 배점이 너무 작다

전체 100점 중 10점이면 사실상 영향력 미미.
consistency가 0점이든 10점이든 최종 점수 차이가 크지 않음.

### 보완 방향

**방향 1: 진단 항목으로 전환 (추천)**

점수에 넣기보다 포트폴리오 진단에서 정성적으로 표현:

```json
{
  "commit_pattern": {
    "status": "규칙적",
    "detail": "활성 기간 중 주 평균 3.2회 커밋",
    "action": null
  }
}
```

**방향 2: 점수에 남기려면 원본 데이터 사용**

샘플이 아닌 커밋 목록 API 원본(`all_author_commits`)의 타임스탬프를 사용.
상세 조회(detail)까지 안 가도 목록 API에 날짜가 포함되어 있으므로 추가 API 호출 불필요.

## 5. 집계 방식

### 현재 로직

```python
# LOC 가중 평균
weighted_sum = sum(score * valid_loc for each repo)
final_score  = weighted_sum / total_loc
# total_loc == 0이면 단순 평균 폴백
```

### 평가

LOC가 큰 레포가 최종 점수를 지배하는 것은 대부분의 경우 합리적.
단, 엣지 케이스 존재:

**자동 생성 코드가 가중치를 왜곡할 수 있음.**
Unity 자동 생성 .cs 파일, CRA 보일러플레이트 등은 ignore_extensions를 통과함.
이런 레포의 LOC가 크면 실제로 코드를 적게 짠 다른 레포가 가중치에서 묻힘.

### 보완 방향

당장 고치기 어렵고 심각도도 높지 않음.
알려진 한계로 인지하되, 자동 생성 패턴이 명확한 경우(예: `Assets/Scripts/Generated/`)를 ignore_paths에 추가하는 것으로 부분 완화 가능.

## 6. 현재 빠져 있는 분석 항목

### 커밋 메시지 분석

Plan3 포트폴리오 진단에서 "커밋 습관"을 항목으로 잡았으나, 현재 extractor에는 커밋 메시지를 분석하는 로직이 없음.

커밋 목록 API에서 메시지 텍스트를 이미 받아오고 있으므로(`c.get("commit", {}).get("message")`), 추가 API 호출 없이 구현 가능:

```python
# 분석 가능 항목
- 평균 메시지 길이
- 무의미 메시지 비율 ("fix", "update", "asdf", "." 등)
- Conventional Commits 패턴 사용 여부 (feat:, fix:, refactor:)
```

### PR/이슈 참여 분석

협업 경험 판별용. 추가 API 호출 필요(`/repos/{owner}/{repo}/pulls`, `/issues`).
Rate Limit 부담이 있으므로 우선순위 낮음. 캡스톤 범위에서는 선택 사항.

### 의존성 파일 파싱

Plan3에서 신규 추가 예정. tree_data 재활용으로 API 호출 불필요.
package.json, requirements.txt, build.gradle 등에서 프레임워크 정보 추출.

### 파일명/폴더명 도메인 감지

Plan3에서 신규 추가 예정. tree_data 재활용으로 API 호출 불필요.
GameManager.cs, PlayerController.cs 등 이름 패턴으로 도메인(게임/웹/ML 등) 감지.
