# Git2Value — GitHubポートフォリオ診断 & 就職戦略レポート

> 最終更新: 2026.05.11 | スペックバージョン: v6.3  
> 対象読者: チームメンバー / 発表準備 / 実行テスト用

---

## 1. プロジェクト紹介

> **新人開発者のためのGitHubポートフォリオ診断 & 就職戦略レポートサービス**

Git2Valueは、応募者のGitHubリポジトリを分析し、以下の3つを提供します。

1. ポートフォリオの強みと改善点
2. 新人基準の職務マッチング結果
3. マッチング職務の市場年収バンド

このシステムは経験者向けの評価ツールではなく、**新人・就活生が自分のGitHubポートフォリオを客観的に点検し、応募方向を決めるためのMVP**です。

---

## 2. なぜ新人専用なのか

| 区分 | 経験者 | 新人 / 就活生 |
|---|---|---|
| GitHubの意味 | 職歴全体の一部 | ほぼ核心的なコードポートフォリオ |
| 評価変数 | 会社経歴、実務経験、交渉力など | プロジェクト品質、技術スタック、開発活動記録 |
| 年収予測 | GitHubだけでは判断不可 | 市場バンドを参考値として提示可能 |
| ユーザーニーズ | 相対的に低い | フィードバックと方向性が強く必要 |

Git2Valueは、GitHubだけで合格可否や正確な年収を予測しません。代わりに、**ポートフォリオの状態、職務の方向性、市場の参考値**を一緒に示すことを目的とします。

---

## 3. サービス全体の流れ

```text
GitHub Username + リポジトリURLリスト（最大3件）
        ↓
GitHubExtractor
  - GitHub APIベースのリポジトリデータ収集
  - README / ファイル構造 / コミット / 言語 / フレームワーク分析
  - チーム・個人リポジトリ判定
  - GitHubスコア算出
        ↓
Profile Builder
  - 分析結果を求人票に近い文体のプロフィールテキストへ変換
  - ドメイン検知結果と技術スタックを結合
        ↓
FAISS Job Matching
  - 求人ベクトルDBとの類似度検索
  - 新人基準で経験者向け求人をフィルタリング
  - ドメイン一致求人をリランキング
        ↓
Final Report
  - モジュールA: ポートフォリオ診断
  - モジュールB: 職務マッチング
  - モジュールC: 市場年収バンド
```

## 4. モジュールA — ポートフォリオ診断

### 4.1 役割

GitHubリポジトリを分析し、リポジトリ別診断、総合スコア、改善ガイドを出力します。

分析対象リポジトリは最大3件です。

```text
推奨入力構成:
- メインプロジェクト 1件
- サブプロジェクト 1〜2件
```

代表プロジェクトを中心に評価するため、多数のリポジトリを一度に入力する方式は制限しています。

---

### 4.2 チーム / 個人リポジトリ判定

応募者本人のコミットだけで作成者数を数えると、実際のチームプロジェクトも個人リポジトリとして誤判定される可能性があります。現在は以下のように用途を分離しています。

```text
応募者本人のコミット一覧
→ 開発活動量、コミットメッセージ、作業一貫性の評価に使用

リポジトリ全体のコミット一覧
→ チーム/個人判定、全体作成者数、協業シグナルの算出に使用
```

作成者が2名以上の場合はチームリポジトリとして判定し、`Fork`かどうかはチーム/個人判定とは分離して補助情報として扱います。

例:

```text
Ttakji_lab-mobile_development_dep [チームリポジトリ · 6名協業]
JuicyMatch [個人リポジトリ]
```

---

### 4.3 GitHubスコア構造

GitHubスコアは100点満点で、3つの軸に分けて算出します。

| 軸 | 配点 | 意味 |
|---|---:|---|
| 開発活動量 | 60点 | 有効コード変更量、分析可能なコミット数、設定・データ系の貢献などに基づく開発活動規模 |
| プロジェクト管理度 | 30点 | テストコード、CI/CD構成、開発継続期間などの管理シグナル |
| 作業一貫性 | 10点 | 応募者のコミット間隔の安定性と作業リズム |

従来の「貢献度」という表現は個人プロジェクトで誤解を招く可能性があるため、現在は**開発活動量**と表現します。これはチーム内の参加率ではなく、GitHub上に表れる有効コード変更量とコミット活動量を意味します。

---

### 4.4 複数リポジトリの最終スコア

複数のリポジトリを入力した場合、単純平均ではなく代表プロジェクトをより大きく反映します。

```text
最終GitHubスコア = 代表プロジェクト（最高点）70% + 全リポジトリ平均 30%
```

これは、新人ポートフォリオでは最も完成度の高い代表プロジェクトが重要である点を反映した方式です。同時に、他のリポジトリの状態も30%反映し、全体管理状態も一部考慮します。

---

### 4.5 Forkリポジトリ補正

Forkリポジトリは、単純コピーやスコア水増しの可能性があるため保守的に扱います。ただし、チーム開発では権限分離、環境差、テストの都合などにより正常にforkを使う場合も多いため、現在はforkであることだけを理由に一律減点しません。

補正基準:

```text
Forkではない
→ 減点なし

Fork + チームリポジトリ
→ チーム平均以上の活動比率なら減点なし
→ 平均より低い場合は活動比率に応じて段階的に減点

Fork + 個人リポジトリ
→ 本人コミット数と有効LOCが十分なら減点を緩和
→ 単純コピーの可能性が高ければ強く減点
```

これにより、オープンソースの単純コピーやスコア水増しは防ぎつつ、実際のチームプロジェクトで発生する正常なfork構造が過度に不利にならないようにしました。

---

### 4.6 リポジトリ別診断項目

共通評価項目:

| 項目 | 説明 |
|---|---|
| README品質 | プロジェクト目的、技術スタック、実行方法、画像/デモの有無 |
| プロジェクト構造 | ディレクトリ構成、`.gitignore`、ファイルごとの平均LOCなど |
| コミットメッセージ | 無意味なメッセージ比率、Conventional Commits適用可能性 |

チームリポジトリの必須点検項目:

| 項目 | 説明 |
|---|---|
| テスト | テストファイルまたはテストフレームワークの使用有無 |
| CI/CD | GitHub Actions、Dockerfile、ビルド自動化シグナル |
| デプロイ | デプロイ設定、ビルド成果物、サービスリンク、itch.ioなど |
| コミットリズム | 応募者基準の週あたりコミット数と協業シグナル |

個人リポジトリではテスト、CI/CD、デプロイ、コミットリズムを強い減点要素として扱わず、チームリポジトリでより重要な協業・運用シグナルとして評価します。

## 5. モジュールB — 職務マッチング

### 5.1 役割

応募者のGitHub分析結果を求人票に近いプロフィールテキストへ変換し、FAISSベクトル検索を用いて類似する求人を探します。

```text
GitHub分析結果
→ プロフィールテキスト変換
→ FAISS類似度検索
→ 新人基準の経験者求人フィルタリング
→ ドメイン一致リランキング
→ 上位求人出力
```

---

### 5.2 プロフィール変換基準

ドメイン検知と技術スタックは以下の優先順位で反映されます。

| 優先順位 | シグナル | 例 |
|---|---|---|
| 1位 | ファイル名 / フォルダ名 | `GameManager.cs`, `PlayerController.cs` → ゲーム開発 |
| 2位 | READMEキーワード | Unity, Spring, React, FastAPIなど |
| 3位 | 依存関係ファイル | `package.json`, `requirements.txt`, `build.gradle`など |
| 4位 | 言語統計 | C#, JavaScript, Pythonなど |

言語だけで職務を判断すると、C#のゲームプロジェクトが一般的なSW開発として誤分類される可能性があるため、ファイル構造とドメインシグナルを併用します。

---

### 5.3 新人基準の経験者求人フィルタリング

Git2Valueは新人・就活生向けのサービスであるため、明確な経験者向け求人は推薦候補から除外します。

除外対象例:

```text
1~4年
3~5年
3年以上
経験者開発者
経験者採用
シニア / Senior
Experienced Engineer
3+ years
```

許容対象例:

```text
新人
ジュニア
経験不問
新人/経験者
経験条件未記載の求人
```

ただし、経験条件が明記されていない求人は新人応募の可能性があると判断し、候補に残します。そのため、出力結果には「明示的な新人求人」と「経験条件未記載求人」が一緒に含まれる可能性があります。

## 6. モジュールC — 市場年収バンド

### 6.1 役割

マッチングされた職務の新人〜3年区間における市場年収レンジを提供します。

重要な原則:

```text
GitHubスコアは年収計算に使用しません。
```

年収は技術力だけで決まるものではなく、会社規模、地域、交渉力、ポジション状況によって大きく変わります。そのため、Git2Valueは正確な個人年収の予測ではなく、**市場参考バンド**のみを提供します。

---

### 6.2 データ基準

- Jumpit 2025求人データに基づく職務別年収データ
- Wanted 2025求人データに基づく職務別年収データ
- 職務別 新人〜3年区間の中央値と現実的な分布範囲

出力例:

```text
マッチング職務 : ゲームクライアント
区間           : 新人 (0〜3年)
市場中央値     : 約3,554万ウォン
実際の分布     : 3,021万〜4,265万ウォン
```

参考職務は、マッチング求人と検知ドメインを基準に別途表示します。

## 9. 実行方法

### 9.1 依存関係のインストール

```bash
pip install -r requirements.txt
```

### 9.2 `.env`設定

プロジェクトルートに`.env`ファイルを作成し、GitHub APIトークンを入力します。

```text
Github_api_token=your_github_token_here
```

`.env`ファイルは絶対にGitHubへアップロードしません。

### 9.3 必須データ確認

以下のファイルが存在する必要があります。

```text
vector/git2value_faiss.index
vector/git2value_metadata.json
data/jumpit_data/
data/wanted_data/
```

### 9.4 実行

`run_git2value.py`下部の入力値を修正します。

```python
TARGET_USERNAME = "github_username"
TARGET_REPOS = [
    "owner/repository/tree/branch"
]
APPLICANT_YEARS = 0
```

実行:

```bash
python run_git2value.py
```

経験フィルタの正規表現を変更した後に結果が不自然な場合は、キャッシュを削除して再実行します。

```bash
del vector\experience_cache.json
python run_git2value.py
```

## 11. 既知の限界

| 限界 | 説明 |
|---|---|
| GitHubがない応募者は分析不可 | 入力データが存在しないため |
| コード全体の品質判定は不可 | 全ソースコードを完全に静的分析するシステムではないため |
| README意味分析の限界 | ルールベースのため、文書の深さまでは完全に判断できない |
| 経験フィルタの限界 | 正規表現ベースのため、特殊な求人表現を見逃す可能性がある |
| 職務マッチングの限界 | 求人データセットのカバレッジに結果が左右される |
| 正確な年収予測は不可 | 年収は会社、地域、交渉力によって変わるため |
| 面接合否予測は不可 | カルチャーフィットや面接力などGitHub外の変数を反映できないため |

## 12. 今後の改善方向

| 方向 | 説明 |
|---|---|
| スコア算出根拠の詳細表示 | 有効LOC、コミット数、テスト/CI/CD有無などをオプションで表示 |
| 経験条件ラベル表示 | `[新人]`, `[経験不問]`, `[経験条件未記載]` などを出力 |
| 職務別フィードバック高度化 | ゲーム、Web、バックエンド、AIなどドメイン別改善ガイドを強化 |
| コード品質分析拡張 | 静的分析ツールと連携してコード品質シグナルを補強 |
| リアルタイム求人連動 | 求人DBを最新データで更新 |

## 13. プロジェクトの位置づけ

Git2Valueは、就活生に合格可否を断定するシステムではありません。  
GitHub上に表れる開発活動、プロジェクト管理状態、職務マッチング可能性、市場年収の参考値を一緒に提供し、**ポートフォリオ改善の方向性を示す診断ツール**です。
