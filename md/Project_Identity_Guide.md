# Git2Value — 프로젝트 정체성 및 에이전트 가이드라인

---

## 1. Git2Value는 무엇인가

Git2Value는 **신입(0~3년) 개발자의 GitHub 레포지토리를 분석·진단·요약하여 취업 전략 정보를 제공하는 시스템**입니다.

### 이 시스템이 하는 것

- GitHub 레포지토리의 **구조적 특성을 요약**합니다 (언어, 프레임워크, 파일 구조, CI/CD, 테스트, 배포)
- 요약된 프로필을 실제 채용 공고와 **유사도 기반으로 매칭**합니다
- 포트폴리오의 **강점과 개선점을 항목별로 진단**합니다
- 매칭된 직무의 **시장 연봉 범위를 참고 정보로 제공**합니다

### 이 시스템이 하지 않는 것

- ❌ 개발자의 **역량을 판단하지 않습니다**
- ❌ 개발자의 **실력을 점수화하지 않습니다**
- ❌ 개발자의 **수준을 등급 매기지 않습니다**
- ❌ "이 사람은 좋은 개발자다 / 나쁜 개발자다"를 **판정하지 않습니다**
- ❌ GitHub 점수로 연봉을 **산출하지 않습니다**

---

## 2. 핵심 구분: "분석/진단" vs "역량 판단"

이 구분이 프로젝트의 가장 중요한 경계선입니다. 에이전트는 모든 작업에서 이 경계를 의식해야 합니다.

|          | 분석/진단 (Git2Value가 하는 것)                     | 역량 판단 (Git2Value가 하지 않는 것) |
| -------- | --------------------------------------------------- | ------------------------------------ |
| **주체** | 레포지토리 (코드 산출물)                            | 개발자 (사람)                        |
| **대상** | 구조, 패턴, 존재 여부                               | 능력, 잠재력, 가치                   |
| **표현** | "테스트 코드가 감지되지 않았습니다"                 | "테스트를 작성할 능력이 부족합니다"  |
| **표현** | "CI/CD 설정이 존재합니다"                           | "이 개발자는 DevOps 역량이 있습니다" |
| **표현** | "이 레포는 Entry 수준의 구성입니다"                 | "이 개발자는 Entry 수준입니다"       |
| **표현** | "게임 개발 공고와 유사도가 높습니다"                | "이 사람은 게임 개발자입니다"        |
| **결론** | "포트폴리오에 이런 점을 보강하면 매칭이 개선됩니다" | "이 사람은 이런 점이 부족합니다"     |

**판별 기준:** 문장의 주어가 "레포지토리/포트폴리오/프로젝트"이면 OK. "개발자/사용자/지원자"의 능력·수준·가치를 직접 평가하는 문장이면 경계를 넘은 것입니다.

---

## 3. 왜 이 구분이 중요한가

### 3-1. 기술적 한계

GitHub 레포지토리는 개발자 역량의 극히 일부만 반영합니다.

- 같은 실력이라도 회사 코드는 GitHub에 올라가지 않음
- 팀 프로젝트에서 본인 기여분만 분리하기 어려움
- 코드 품질(가독성, 설계, 아키텍처)은 파일 구조와 LOC로 판단 불가
- 면접 능력, 커뮤니케이션, 문제 해결 과정은 GitHub에 남지 않음

**따라서:** "GitHub 분석 결과 = 개발자 역량"이라는 등식을 세우는 것은 기술적으로 부당합니다.

### 3-2. 서비스 신뢰도

"당신은 Entry 수준 개발자입니다"라고 판정하면 사용자가 반발하거나 낙담합니다. "당신의 포트폴리오는 Entry 수준 구성입니다. 이렇게 보강하면 Competitive에 도달합니다"라고 하면 **행동 가능한 피드백**이 됩니다. 역량 판단은 서비스 신뢰도를 깎고, 분석/진단은 신뢰도를 높입니다.

### 3-3. 법적·윤리적 리스크

자동화된 시스템이 사람의 역량을 점수화하여 채용 의사결정에 영향을 주면, AI 윤리·공정성 문제가 됩니다. Git2Value는 의도적으로 이 영역을 피합니다.

## 4. 에이전트 가이드라인

### 가이드라인 1: 문장의 주어를 항상 확인하라

문서, 코드 주석, 출력 메시지, 발표 자료를 작성할 때 **주어가 사람인지 산출물인지** 확인합니다.

```
✅ "이 레포지토리의 README는 200자 이상이며 스크린샷을 포함하고 있어 양호합니다."
❌ "이 개발자는 README 작성 능력이 양호합니다."

✅ "포트폴리오 구성이 Competitive 수준에 해당합니다."
❌ "이 지원자는 Competitive 수준의 개발자입니다."

✅ "이 프로젝트에서 테스트 코드가 감지되지 않았습니다. 추가를 권장합니다."
❌ "이 개발자는 테스트 작성 능력이 부족합니다."
```

### 가이드라인 2: github_score는 "레포지토리 점수"이지 "개발자 점수"가 아니다

`github_score`는 분석된 레포지토리들의 구조적 특성을 수치화한 것입니다. 이 점수가 높다고 좋은 개발자, 낮다고 나쁜 개발자가 아닙니다.

```
✅ "GitHub 종합 점수: 79점 / 100점 — 분석된 레포지토리의 기여도·완성도·일관성 종합"
❌ "개발 역량 점수: 79점 / 100점"

✅ "점수가 낮은 이유는 테스트 코드와 CI/CD가 감지되지 않았기 때문입니다."
❌ "점수가 낮은 이유는 개발 역량이 부족하기 때문입니다."
```

### 가이드라인 3: 등급(Entry/Competitive/Top)은 "포트폴리오 구성 수준"이다

등급은 레포지토리 구성(README, CI/CD, 테스트, 배포 등)의 완성도를 분류한 것이지, 개발자의 능력 등급이 아닙니다.

```
✅ "현재 포트폴리오 구성은 Entry 수준입니다. CI/CD 또는 배포 경험 추가 시 Competitive에 도달합니다."
❌ "현재 개발 실력은 Entry 수준입니다."

✅ "Competitive 수준의 포트폴리오를 보유하고 있어 시리즈B 이상 스타트업에서 경쟁력이 있습니다."
❌ "Competitive 수준의 개발자이므로 시리즈B에 취업 가능합니다."
```

### 가이드라인 4: 직무 매칭은 "유사도 기반 추천"이지 "적성 판단"이 아니다

FAISS 유사도 매칭은 "이 레포지토리의 기술적 특성이 이 공고와 텍스트적으로 유사하다"는 의미입니다. "이 사람이 이 직무에 적합하다"는 뜻이 아닙니다.

```
✅ "프로필과 가장 유사한 공고는 [A사] 백엔드 개발자입니다."
❌ "당신에게 가장 적합한 직무는 백엔드 개발자입니다."

✅ "게임 개발 공고와의 유사도가 높습니다. 해당 방향 지원을 고려해볼 수 있습니다."
❌ "당신은 게임 개발자로 적합합니다."
```

### 가이드라인 5: 연봉은 "시장 참고 정보"이지 "개인 예측"이 아니다

연봉 밴드는 직무별 시장 중앙값이며, GitHub 점수와 의도적으로 분리되어 있습니다. 특정 사용자가 이 연봉을 받을 것이라는 예측이 아닙니다.

```
✅ "서버/백엔드 직무의 신입 시장 연봉 범위는 약 3,145만~4,440만원입니다."
❌ "당신의 예상 연봉은 3,700만원입니다."
❌ "GitHub 점수 79점이므로 시장 중앙값보다 높은 연봉을 기대할 수 있습니다."
```

### 가이드라인 6: 진단의 목적은 "행동 유도"이지 "평가"가 아니다

모든 진단 항목의 최종 목적은 **사용자가 포트폴리오를 개선하기 위해 구체적으로 무엇을 할 수 있는지 안내**하는 것입니다.

```
✅ "테스트 코드가 감지되지 않았습니다. pytest 또는 Jest로 핵심 로직 1~2개에 단위 테스트를 추가하면 포트폴리오 완성도가 올라갑니다."
❌ "테스트 코드가 없어 미흡합니다."  (행동 안내 없는 단순 평가)

✅ "커밋 메시지 중 42%가 'fix', 'update' 등 무의미 메시지입니다. Conventional Commits 형식(feat:/fix:/refactor:)을 적용하면 가독성이 크게 개선됩니다."
❌ "커밋 메시지 습관이 나쁩니다."
```

### 가이드라인 7: 부정적 결과를 전달할 때의 프레이밍

나쁜 소식도 전달해야 하지만, "당신이 부족하다"가 아니라 **"포트폴리오에 이 부분이 비어 있다 → 이렇게 채우면 된다"**의 구조로 전달합니다.

```
✅ "현재 포트폴리오에서 배포 경험이 감지되지 않았습니다. Dockerfile 하나를 추가하면 이 항목이 '양호'로 전환됩니다."
❌ "배포 경험이 없어 경쟁력이 부족합니다."

✅ "팀 프로젝트가 감지되지 않아 Competitive 등급에는 도달하지 않습니다. 팀 프로젝트 1개를 추가하면 등급이 올라갈 수 있습니다."
❌ "협업 경험이 없어 한계가 있습니다."
```

### 가이드라인 8: 시스템의 한계를 정직하게 인정하라

Git2Value가 할 수 없는 것을 할 수 있다고 표현하면 안 됩니다.

```
✅ "이 시스템은 코드의 품질(가독성, 설계 패턴, 아키텍처)을 직접 평가하지 않습니다. 파일 구조와 통계적 지표에 기반한 간접 평가입니다."
❌ "이 시스템은 코드 품질을 분석합니다."

✅ "GitHub에 올라가지 않은 프로젝트, 회사 내부 코드, 면접 퍼포먼스는 분석 범위 밖입니다."
❌ (이 한계를 언급하지 않고 "종합적인 역량 분석"이라고 표현하는 것)
```

## 5. 용어 사전: 써도 되는 표현 / 쓰면 안 되는 표현

| 상황        | ✅ 사용 가능                              | ❌ 사용 금지                       |
| ----------- | ----------------------------------------- | ---------------------------------- |
| 점수 설명   | 레포지토리 분석 점수, 포트폴리오 점수     | 개발 역량 점수, 실력 점수          |
| 등급 설명   | 포트폴리오 구성 수준, 포트폴리오 완성도   | 개발자 수준, 개발자 등급           |
| 매칭 설명   | 유사한 공고, 매칭되는 직무                | 적합한 직무, 추천 직무             |
| 연봉 설명   | 시장 연봉 범위, 참고 정보                 | 예상 연봉, 추천 연봉               |
| 진단 설명   | 포트폴리오 진단, 항목별 체크리스트        | 역량 평가, 능력 진단               |
| 부족 항목   | 감지되지 않았습니다, 추가를 권장합니다    | 부족합니다, 능력이 없습니다        |
| 좋은 항목   | 양호한 구성입니다, 경쟁력 있는 포트폴리오 | 뛰어난 개발자, 능력이 우수         |
| 시스템 소개 | 포트폴리오 분석 시스템, 취업 전략 리포트  | 역량 평가 시스템, 개발자 평가 도구 |
| 사용자 호칭 | 지원자, 사용자                            | 피평가자                           |

## 6. 적용 범위

이 가이드라인은 다음 모든 작업에 적용됩니다:

- **코드 작성/검증**: 출력 메시지, 변수명, 주석, 로그 메시지
- **문서 작성**: HandOff, Spec, 계획 파일, 논문, 발표 자료
- **설계 논의**: 새 기능 제안, 평가 기준 설계, 출력 구조 결정
- **발표 대응**: 질문 답변 준비, 스크립트 작성
- **사용자 피드백 검토**: 팀원/외부 피드백의 표현이 역량 판단에 해당하면 분석/진단 프레이밍으로 재구성

## 7. 자기 점검 체크리스트

에이전트가 문서·코드·출력을 생성한 후 다음을 확인합니다:

- [ ] 문장의 주어가 "레포지토리/포트폴리오/프로젝트"인가? ("개발자/사용자"의 능력을 평가하는 문장은 없는가?)
- [ ] `github_score`를 "개발자 점수"가 아닌 "레포지토리 분석 점수"로 표현했는가?
- [ ] 등급을 "포트폴리오 구성 수준"으로 표현했는가?
- [ ] 직무 매칭을 "유사도 기반 추천"으로 표현했는가?
- [ ] 연봉을 "시장 참고 정보"로 표현했는가?
- [ ] 진단 결과에 **행동 안내**(어떻게 개선할 수 있는지)가 포함되어 있는가?
- [ ] 부정적 결과를 "비어 있다 → 채우면 된다" 구조로 전달했는가?
- [ ] 시스템의 한계를 숨기지 않았는가?

---

## 8. 이 문서의 위치

이 문서는 **프로젝트의 모든 다른 문서보다 우선**합니다. 다른 계획 파일이나 HandOff에서 역량 판단에 해당하는 표현이 있으면, 이 문서의 원칙에 맞게 수정해야 합니다.

새 세션을 시작할 때 이 문서를 `Session_Handoff.md`와 함께 첨부하면, 에이전트가 프로젝트의 정체성을 정확히 인지한 상태에서 작업을 시작할 수 있습니다.
