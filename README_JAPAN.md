## 1. 一行紹介[cite: 1]

> **新人開発者のためのGitHubポートフォリオ診断＆就職戦略レポートサービス**[cite: 1]

GitHubリポジトリを分析し、就活生に以下の3つをお知らせします:[cite: 1]
1. どのような職務の求人とマッチングするか[cite: 1]
2. ポートフォリオの強みと弱みは何か[cite: 1]
3. 該当職務の市場年収レンジはいくらか[cite: 1]

## 2. なぜ新人専用なのか[cite: 1]

| | 経験者 (中途) | 新人(就活生) |
|---|---|---|
| GitHubの意味[cite: 1] | 全体の力量のごく一部[cite: 1] | 事実上唯一のコードポートフォリオ[cite: 1] |

## 3. サービスの全体構造[cite: 1]

```text
GitHub Username + リポジトリURLリスト[cite: 1]
        ↓
┌─────────────────────────────────────────────┐
│           GitHubExtractor                   │
│  - GitHub APIの非同期収集                    │
│  - 均等なコミットサンプリング + SHA重複排除   │
│  - スコア算出（貢献度 / 成熟度 / 一貫性）     │
│  - 依存関係ファイルのパーシング               │
│  - ファイル名/フォルダ名のドメイン検知        │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│           プロフィール変換レイヤー            │
│  build_profile_text()                       │
│  - 抽出データを採用求人の文体に変換           │
│  - ドメイン検知 → 言語+ドメインの結合表現      │
│  - READMEの残量に基づく分岐処理               │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│           FAISS ベクトルマッチング           │
│  jhgan/ko-sroberta-multitask 埋め込み        │
│  3,400件の実際の採用求人インデックス         │
│  (Wanted 2,000 + Jumpit 1,000 + Remember 400)│
└─────────────────────────────────────────────┘
        ↓
┌────────────────┬────────────────┬────────────────┐
│  モジュール A   │  モジュール B   │  モジュール C   │
│  職務マッチング  │  ポートフォリオ診断│  市場年収バンド  │
│  (上位5件の求人) │  (チェックリスト) │  (独立照会)      │
└────────────────┴────────────────┴────────────────┘
        ↓
      最終統合レポート[cite: 1]
```

**核心設計原則:** 3つのモジュールは完全に独立しています。[cite: 1] 1つが不正確でも残りのモジュールを汚染しません。[cite: 1]

## 4. モジュールA: 職務マッチング[cite: 1]

### 役割[cite: 1]
応募者のGitHubプロフィールを3,400件の採用求人と比較し、最も類似している求人の上位5件を推薦します。[cite: 1]

### 技術構成[cite: 1]

**埋め込み(Embedding)モデル:** `jhgan/ko-sroberta-multitask` (韓国語特化)[cite: 1]
**ベクトルDB:** FAISS (CPU)[cite: 1]
**類似度:** コサイン類似度[cite: 1]

### プロフィール変換レイヤー[cite: 1]

GitHubから抽出したデータを、採用求人と**同じ文体**のテキストに変換します。[cite: 1]
この変換を行わないと、GitHubのテキスト("Python (45%), C# (30%)")と求人のテキスト("3年以上のSpring Boot経験者優遇")の文体が異なり、意味のある類似度が算出されません。[cite: 1]

変換時、以下のシグナルを優先順位に従って結合します:[cite: 1]

| 優先順位 | シグナル | 例 |
|---|---|---|
| 1位[cite: 1] | ファイル名/フォルダ名のドメイン検知[cite: 1] | GameManager.cs, PlayerController.cs → "ゲーム開発"[cite: 1] |
| 2位[cite: 1] | READMEテキストのキーワード[cite: 1] | "Unity UI連携ガイド" → ゲームドメインの補強[cite: 1] |
| 3位[cite: 1] | 依存関係ファイル (package.jsonなど)[cite: 1] | React, FastAPI → フレームワークの特定[cite: 1] |
| 4位[cite: 1] | 言語統計[cite: 1] | C# 60%, Python 25% → フォールバック(代替手段)[cite: 1] |

**変換例:**[cite: 1]
- 変換前: `"主要技術スタック: C# (92%)\n\n[repo要約]: REST APIサーバーを構築しました"`[cite: 1]
- 変換後: `"C#ベースのゲーム開発経験。Unity連動設計。テストコード作成経験保有。"`[cite: 1]

### ドメイン検知[cite: 1]

言語だけではドメインを誤分類するケースがあります（例: C#のゲームリポジトリ → SW開発と誤分類）。[cite: 1]
ファイル/フォルダ名のパターンでドメインを検知し、これを防止します。[cite: 1]

```python
DOMAIN_SIGNALS = {
    "ゲーム開発":    ["game", "player", "enemy", "scene", "inventory", "combat", "spawn", ...],
    "ウェブフロントエンド": ["component", "page", "layout", "header", "navbar", "modal", ...],
    "サーバー/バックエンド":   ["controller", "service", "repository", "middleware", "router", ...],
    "ML/AI":        ["model", "train", "dataset", "inference", "embedding", ...],
    "モバイルアプリ":     ["activity", "fragment", "viewmodel", "storyboard", ...],
    "DevOps/インフラ": ["terraform", "ansible", "helm", "k8s", "pipeline", ...],
}
# 最小2つ以上マッチングした場合にのみ、該当ドメインとして認定[cite: 1]
```

### マッチング求人のパターン分析[cite: 1]

上位5件のマッチング求人の共通点を要約して提供します。[cite: 1]
特定の会社を「ティア（階層）」に分類しないため、論争を招くことなく市場感覚を伝えます。[cite: 1]

```json
{
  "top_5_pattern": {
    "common_tech_stack": ["Python", "Docker", "AWS"],
    "company_types": ["シリーズBスタートアップ3社", "中堅IT企業2社"],
    "common_requirements": "REST API設計経験、協業ツールの使用経験"
  }
}
```

## 5. モジュールB: ポートフォリオ診断[cite: 1]

### 役割[cite: 1]
GitHubリポジトリを分析し、項目別のチェックリスト、改善ガイド、そして市場の期待レベルをお知らせします。[cite: 1]

### 診断項目[cite: 1]

| 診断項目 | 判別方法 | データソース |
|---|---|---|
| READMEの品質[cite: 1] | クレンジング後のテキスト長、スクリーンショット/GIFの有無[cite: 1] | readme_data[cite: 1] |
| プロジェクト構造[cite: 1] | ディレクトリのモジュール化、.gitignoreの存在、ファイルあたりの平均LOC[cite: 1] | tree_data[cite: 1] |
| テストの作成[cite: 1] | testファイル / 全ソースファイルの比率[cite: 1] | tree_data[cite: 1] |
| CI/CDの構成[cite: 1] | GitHub Actions / Dockerfileの存在 + ファイルサイズ > 200B[cite: 1] | tree_data[cite: 1] |
| コミットの習慣[cite: 1] | コミットメッセージの平均文字数、無意味なメッセージ("fix", "update")の比率[cite: 1] | commits API[cite: 1] |
| デプロイ経験[cite: 1] | Dockerfile, docker-compose, Vercel/Netlify設定の存在[cite: 1] | tree_data[cite: 1] |
| 協業経験[cite: 1] | チームプロジェクトリポジトリでのPR/Issueへの参加パターン[cite: 1] | commits API[cite: 1] |

### 出力例[cite: 1]

```json
{
  "readme_quality": {
    "status": "良好",
    "detail": "平均680文字、2つのリポジトリにスクリーンショットを含む",
    "action": null
  },
  "test_coverage": {
    "status": "不十分",
    "detail": "3つのリポジトリのうちテストファイルが存在するのは0件",
    "action": "主力のプロジェクトにpytest/Jestテストを追加してください。"
  },
  "commit_quality": {
    "status": "改善が必要",
    "detail": "コミットメッセージのうち42%が無意味なメッセージ",
    "action": "Conventional Commits形式(feat:, fix:, refactor:)を適用してみてください。"
  }
}
```

### 期待レベルガイド[cite: 1]

ポートフォリオの完成度に応じて、市場でどのレベルに位置するかを案内します。[cite: 1]

| レベル | 満たすべき条件 | 説明 |
|---|---|---|
| **Entry**[cite: 1] | READMEが存在、プロジェクト1〜2個[cite: 1] | 中小/中堅SI、一般スタートアップに志願可能なレベル[cite: 1] |
| **Competitive**[cite: 1] | + テストコード + CI/CD + デプロイ経験[cite: 1] | シリーズB以上のスタートアップ、ITサービス企業で競争力のあるレベル[cite: 1] |
| **Top**[cite: 1] | + オープンソースへの貢献 + 技術ブログ + 複数の完成プロジェクト[cite: 1] | 大手テック企業の書類選考を通過可能なレベル[cite: 1] |

## 6. モジュールC: 市場年収バンド[cite: 1]

### 役割[cite: 1]
マッチングされた職務の新卒市場年収の範囲を、**GitHubのスコアとは無関係に**独立して提供します。[cite: 1]

### なぜGitHubのスコアで年収を計算しないのか[cite: 1]

- GitHubのスコアがXの人が、実際の年収Yを受け取っているというデータは存在しません。[cite: 1]
- 年収は技術力の関数ではありません — 同じ実力でも、会社、地域、交渉力によって2〜3倍の差が生じます。[cite: 1]
- 根拠のない精密な数字("推奨年収4,823万ウォン")は、サービスの信頼性を損ないます。[cite: 1]

### データの基盤[cite: 1]

Jumpit・Wantedの2025年の採用求人から抽出した、職務別・年次別の年収の中央値を使用します。[cite: 1]
両プラットフォームの交差検証の結果、新人区間は誤差率±5%以内に収束しています。[cite: 1]

### 出力例[cite: 1]

```json
{
  "market_salary_band": {
    "matched_category": "サーバー/バックエンド",
    "experience_level": "新人 (0〜3年)",
    "salary_range": {
      "jumpit_median": 36498644,
      "wanted_median": 38354225,
      "combined_range": "3,500万 〜 3,800万ウォン"
    },
    "source": "Jumpit・Wanted 2025採用求人ベース"
  },
  "category_comparison": [
    {"category": "人工知能/機械学習", "junior_range": "3,900万 〜 4,100万ウォン"},
    {"category": "サーバー/バックエンド",  "junior_range": "3,500万 〜 3,800万ウォン"},
    {"category": "フロントエンド",       "junior_range": "3,400万 〜 3,500万ウォン"},
    {"category": "QAエンジニア",     "junior_range": "3,100万 〜 3,300万ウォン"}
  ]
}
```

職務間の比較情報を併せて提供することで、職務選択の参考になるようにします。[cite: 1]

## 7. GitHub分析エンジンの詳細[cite: 1]

### スコア構造 (3軸分解)[cite: 1]

| 軸 | 配点 | 算出方式 |
|---|---|---|
| contribution (貢献度)[cite: 1] | 最大60点[cite: 1] | LOC 70% + コミット数 30% ブレンディング[cite: 1] |
| quality (成熟度)[cite: 1] | 最大30点[cite: 1] | CI/CDの実質性 + テスト比率 + メンテナンス期間[cite: 1] |
| consistency (一貫性)[cite: 1] | 最大10点[cite: 1] | コミット間隔の標準偏差に基づく[cite: 1] |

### アンチチート(不正防止)[cite: 1]

- **Fork検知:** forkされたリポジトリは貢献度にのみ70%減点（オープンソースへの貢献は認める）[cite: 1]
- **オーナーシップ確認:** 最初のコミット日とリポジトリ作成日を比較 → 30日以上の差がある場合は警告[cite: 1]
- **SHAの重複排除:** リポジトリ間で同一コミットが重複して集計されるのを防止[cite: 1]
- **ボイラープレートの除去:** CRA、フレームワークの基本テキストを自動フィルタリング[cite: 1]

### コミットサンプリング[cite: 1]

全コミットを初期/中間/最近の3区間に分け、各区間から最大25個ずつ均等に抽出します。[cite: 1]
最近のコミットだけを見る偏りを防ぎます。[cite: 1]

### Rate Limitの対応[cite: 1]

すべてのGitHub API呼び出しに`Retry-After`ヘッダーの解析 + 指数バックオフ（最大3回）を適用。[cite: 1]
3回失敗した場合は該当リポジトリを明示的にスキップし、警告を出力します。[cite: 1]

## 8. README活用戦略[cite: 1]

```text
_clean_markdown() 後のテキスト長[cite: 1]
    ↓
[200文字以上] → クレンジング済みテキスト + 構造化データでプロフィール生成[cite: 1]
    ↓
[50〜200文字]  → 構造化データ(言語、依存関係、ドメイン検知)ベースのテンプレートプロフィール[cite: 1]
    ↓
[50文字未満] → 依存関係ファイルのパーシング + ドメイン検知を試行[cite: 1]
              ├─ シグナルあり → 最小プロフィール生成[cite: 1]
              └─ シグナルなし → "詳細分析不可"と正直に表示[cite: 1]
```

**原則:** 存在しない情報を作り出しません。[cite: 1] 情報が不足している場合は、不足していると表示します。[cite: 1]

## 11. 実行方法[cite: 1]

### 事前準備[cite: 1]
1. `.env`ファイルに`Github_api_token`を設定[cite: 1]
2. `pip install -r requirements.txt`を実行[cite: 1]
3. `vector/`フォルダにFAISSインデックスファイルが存在することを確認[cite: 1]

### 実行[cite: 1]
```bash
# E2Eパイプライン (全体の流れ)
python run_git2value.py

# GitHub分析のみを単独実行
python github_extractor.py

# 年収バンド照会のみを単独テスト
python valuation_engine.py
```

`run_git2value.py`の`__main__`ブロックで`TARGET_USERNAME`、`TARGET_REPOS`、`APPLICANT_YEARS`を修正して分析対象を変更します。[cite: 1]

## 12. キャプストーンデザイン戦略[cite: 1]

### 発表構造[cite: 1]

```text
1. 問題定義[cite: 1]
   "新人開発者が自身のポートフォリオの市場競争力を把握できない"[cite: 1]

2. 現場での検証[cite: 1]
   現役の採用担当者へのインタビューを通じ、問題が実在することを確認[cite: 1]
   (→ チームでインタビュー1〜2件の確保が必要)[cite: 1]

3. 解決策[cite: 1]
   技術アーキテクチャの説明 (FAISS、埋め込み、非同期クローリングなど)[cite: 1]

4. 産業界との連携[cite: 1]
   現役のフィードバックを診断基準に反映[cite: 1]
   就活生5〜10名を対象とした実使用テストの結果[cite: 1]

```

|---|---|

| **ユーザー検証**[cite: 1] | 就活生5〜10名を対象とした実際のGitHub分析 → フィードバックの収集[cite: 1] |

| 拡張方向 | 説明 |
|---|---|

| 経験者（中途）への拡張[cite: 1] | LinkedIn/履歴書との結合により、経験者の分析が可能[cite: 1] |

## 13. 既知の限界[cite: 1]

このシステムが**できないこと**を明確に認識して使用する必要があります。[cite: 1]

| 限界 | 理由 |
|---|---|
| GitHubを持たない応募者の分析は不可[cite: 1] | 入力データ自体が存在しないため[cite: 1] |
| コード全体の品質判定は不可[cite: 1] | サンプルに基づく間接評価という本質的な限界があるため[cite: 1] |
| 正確な年収予測は不可[cite: 1] | GitHubのスコアと年収の間の検証された相関関係が不在のため[cite: 1] |
| GitHubを使用しない開発者はカバー不可[cite: 1] | 新人の中でもGitHubを積極的に管理している割合は一部に過ぎないため[cite: 1] |
| 面接の合否予測は不可[cite: 1] | カルチャーフィット、面接でのパフォーマンスなど、GitHub以外の変数が存在するため[cite: 1] |
