## 1. 一行紹介

> **新人開発者のためのGitHubポートフォリオ診断＆就職戦略レポートサービス**

GitHubリポジトリを分析し、就活生に以下の3つをお知らせします:
1. どのような職務の求人とマッチングするか
2. ポートフォリオの強みと弱みは何か
3. 該当職務の市場年収レンジはいくらか

---

## 2. なぜ新人専用なのか

| | 経験者 (中途) | 新人(就活生) |
|---|---|---|
| GitHubの意味 | 全体の力量のごく一部 | 事実上唯一のコードポートフォリオ |
| 年収の決定変数 | 職歴、交渉力、ストックオプションなどGitHub以外の変数が支配的 | 会社のティア（階層）ごとのバンドが狭く、範囲の提示が現実的 |
| レベル推定の必要性 | シニア/ジュニアの区別が必要（GitHubでは不可能） | 不要 — 全員が新人 |
| ユーザーのニーズ | 弱い（既にLinkedInやヘッドハンターが存在） | **強い**（就活生はフィードバックに飢えている） |

## 3. サービスの全体構造

```text
GitHub Username + リポジトリURLリスト
        ↓
┌─────────────────────────────────────────────┐
│           GitHubExtractor                   │
│  - GitHub APIの非同期収集                    │
│  - 均等なコミットサンプリング + SHA重複排除   │
│  - スコア算出（貢献度 / 成熟度 / 一貫性）     │
│  - 依存関係ファイルのパーシング               │
│  - ファイル名/フォルダ名のドメイン検知        │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│           プロフィール変換レイヤー            │
│  build_profile_text()                       │
│  - 抽出データを採用求人の文体に変換           │
│  - ドメイン検知 → 言語+ドメインの結合表現      │
│  - READMEの残量に基づく分岐処理               │
└─────────────────────────────────────────────┘
        ↓
┌─────────────────────────────────────────────┐
│           FAISS ベクトルマッチング           │
│  jhgan/ko-sroberta-multitask 埋め込み        │
│  3,400件の実際の採用求人インデックス         │
│  (Wanted 2,000 + Jumpit 1,000 + Remember 400)│
└─────────────────────────────────────────────┘
        ↓
┌────────────────┬────────────────┬────────────────┐
│  モジュール A   │  モジュール B   │  モジュール C   │
│  職務マッチング  │  ポートフォリオ診断│  市場年収バンド  │
│  (上位5件の求人) │  (チェックリスト) │  (独立照会)      │
└────────────────┴────────────────┴────────────────┘
        ↓
      最終統合レポート
```

**核心設計原則:** 3つのモジュールは完全に独立しています。 1つが不正確でも残りのモジュールを汚染しません。

## 4. モジュールA: 職務マッチング

### 役割
応募者のGitHubプロフィールを3,400件の採用求人と比較し、最も類似している求人の上位5件を推薦します。

### 技術構成

**埋め込み(Embedding)モデル:** `jhgan/ko-sroberta-multitask` (韓国語特化)
**ベクトルDB:** FAISS (CPU)
**類似度:** コサイン類似度

### プロフィール変換レイヤー

GitHubから抽出したデータを、採用求人と**同じ文体**のテキストに変換します。
この変換を行わないと、GitHubのテキスト("Python (45%), C# (30%)")と求人のテキスト("3年以上のSpring Boot経験者優遇")の文体が異なり、意味のある類似度が算出されません。

変換時、以下のシグナルを優先順位に従って結合します:

| 優先順位 | シグナル | 例 |
|---|---|---|
| 1位 | ファイル名/フォルダ名のドメイン検知 | GameManager.cs, PlayerController.cs → "ゲーム開発" |
| 2位 | READMEテキストのキーワード | "Unity UI連携ガイド" → ゲームドメインの補強 |
| 3位 | 依存関係ファイル (package.jsonなど) | React, FastAPI → フレームワークの特定 |
| 4位 | 言語統計 | C# 60%, Python 25% → フォールバック(代替手段) |

**変換例:**
- 変換前: `"主要技術スタック: C# (92%)\n\n[repo要約]: REST APIサーバーを構築しました"`
- 変換後: `"C#ベースのゲーム開発経験。Unity連動設計。テストコード作成経験保有。"`

### ドメイン検知

言語だけではドメインを誤分類するケースがあります（例: C#のゲームリポジトリ → SW開発と誤分類）。
ファイル/フォルダ名のパターンでドメインを検知し、これを防止します。

```python
DOMAIN_SIGNALS = {
    "ゲーム開発":    ["game", "player", "enemy", "scene", "inventory", "combat", "spawn", ...],
    "ウェブフロントエンド": ["component", "page", "layout", "header", "navbar", "modal", ...],
    "サーバー/バックエンド":   ["controller", "service", "repository", "middleware", "router", ...],
    "ML/AI":        ["model", "train", "dataset", "inference", "embedding", ...],
    "モバイルアプリ":     ["activity", "fragment", "viewmodel", "storyboard", ...],
    "DevOps/インフラ": ["terraform", "ansible", "helm", "k8s", "pipeline", ...],
}
# 最小2つ以上マッチングした場合にのみ、該当ドメインとして認定
```

### マッチング求人のパターン分析

上位5件のマッチング求人の共通点を要約して提供します。
特定の会社を「ティア（階層）」に分類しないため、論争を招くことなく市場感覚を伝えます。

```json
{
  "top_5_pattern": {
    "common_tech_stack": ["Python", "Docker", "AWS"],
    "company_types": ["シリーズBスタートアップ3社", "中堅IT企業2社"],
    "common_requirements": "REST API設計経験、協業ツールの使用経験"
  }
}
```

## 5. モジュールB: ポートフォリオ診断

### 役割
GitHubリポジトリを分析し、項目別のチェックリスト、改善ガイド、そして市場の期待レベルをお知らせします。

### 診断項目

| 診断項目 | 判別方法 | データソース |
|---|---|---|
| READMEの品質 | クレンジング後のテキスト長、スクリーンショット/GIFの有無 | readme_data |
| プロジェクト構造 | ディレクトリのモジュール化、.gitignoreの存在、ファイルあたりの平均LOC | tree_data |
| テストの作成 | testファイル / 全ソースファイルの比率 | tree_data |
| CI/CDの構成 | GitHub Actions / Dockerfileの存在 + ファイルサイズ > 200B | tree_data |
| コミットの習慣 | コミットメッセージの平均文字数、無意味なメッセージ("fix", "update")の比率 | commits API |
| デプロイ経験 | Dockerfile, docker-compose, Vercel/Netlify設定の存在 | tree_data |
| 協業経験 | チームプロジェクトリポジトリでのPR/Issueへの参加パターン | commits API |

### 出力例

```json
{
  "readme_quality": {
    "status": "良好",
    "detail": "平均680文字、2つのリポジトリにスクリーンショットを含む",
    "action": null
  },
  "test_coverage": {
    "status": "不十分",
    "detail": "3つのリポジトリのうちテストファイルが存在するのは0件",
    "action": "主力のプロジェクトにpytest/Jestテストを追加してください。"
  },
  "commit_quality": {
    "status": "改善が必要",
    "detail": "コミットメッセージのうち42%が無意味なメッセージ",
    "action": "Conventional Commits形式(feat:, fix:, refactor:)を適用してみてください。"
  }
}
```

### 期待レベルガイド

ポートフォリオの完成度に応じて、市場でどのレベルに位置するかを案内します。

| レベル | 満たすべき条件 | 説明 |
|---|---|---|
| **Entry** | READMEが存在、プロジェクト1〜2個 | 中小/中堅SI、一般スタートアップに志願可能なレベル |
| **Competitive** | + テストコード + CI/CD + デプロイ経験 | シリーズB以上のスタートアップ、ITサービス企業で競争力のあるレベル |
| **Top** | + オープンソースへの貢献 + 技術ブログ + 複数の完成プロジェクト | 大手テック企業の書類選考を通過可能なレベル |

## 6. モジュールC: 市場年収バンド

### 役割
マッチングされた職務の新卒市場年収の範囲を、**GitHubのスコアとは無関係に**独立して提供します。

### なぜGitHubのスコアで年収を計算しないのか

- GitHubのスコアがXの人が、実際の年収Yを受け取っているというデータは存在しません。
- 年収は技術力の関数ではありません — 同じ実力でも、会社、地域、交渉力によって2〜3倍の差が生じます。
- 根拠のない精密な数字("推奨年収4,823万ウォン")は、サービスの信頼性を損ないます。

### データの基盤

Jumpit・Wantedの2025年の採用求人から抽出した、職務別・年次別の年収の中央値を使用します。
両プラットフォームの交差検証の結果、新人区間は誤差率±5%以内に収束しています。

### 出力例

```json
{
  "market_salary_band": {
    "matched_category": "サーバー/バックエンド",
    "experience_level": "新人 (0〜3年)",
    "salary_range": {
      "jumpit_median": 36498644,
      "wanted_median": 38354225,
      "combined_range": "3,500万 〜 3,800万ウォン"
    },
    "source": "Jumpit・Wanted 2025採用求人ベース"
  },
  "category_comparison": [
    {"category": "人工知能/機械学習", "junior_range": "3,900万 〜 4,100万ウォン"},
    {"category": "サーバー/バックエンド",  "junior_range": "3,500万 〜 3,800万ウォン"},
    {"category": "フロントエンド",       "junior_range": "3,400万 〜 3,500万ウォン"},
    {"category": "QAエンジニア",     "junior_range": "3,100万 〜 3,300万ウォン"}
  ]
}
```

職務間の比較情報を併せて提供することで、職務選択の参考になるようにします。

## 7. GitHub分析エンジンの詳細

### スコア構造 (3軸分解)

| 軸 | 配点 | 算出方式 |
|---|---|---|
| contribution (貢献度) | 最大60点 | LOC 70% + コミット数 30% ブレンディング |
| quality (成熟度) | 最大30点 | CI/CDの実質性 + テスト比率 + メンテナンス期間 |
| consistency (一貫性) | 最大10点 | コミット間隔の標準偏差に基づく |

### アンチチート(不正防止)

- **Fork検知:** forkされたリポジトリは貢献度にのみ70%減点（オープンソースへの貢献は認める）
- **オーナーシップ確認:** 最初のコミット日とリポジトリ作成日を比較 → 30日以上の差がある場合は警告
- **SHAの重複排除:** リポジトリ間で同一コミットが重複して集計されるのを防止
- **ボイラープレートの除去:** CRA、フレームワークの基本テキストを自動フィルタリング

### コミットサンプリング

全コミットを初期/中間/最近の3区間に分け、各区間から最大25個ずつ均等に抽出します。
最近のコミットだけを見る偏りを防ぎます。

### Rate Limitの対応

すべてのGitHub API呼び出しに`Retry-After`ヘッダーの解析 + 指数バックオフ（最大3回）を適用。
3回失敗した場合は該当リポジトリを明示的にスキップし、警告を出力します。

## 8. README活用戦略

```text
_clean_markdown() 後のテキスト長
    ↓
[200文字以上] → クレンジング済みテキスト + 構造化データでプロフィール生成
    ↓
[50〜200文字]  → 構造化データ(言語、依存関係、ドメイン検知)ベースのテンプレートプロフィール
    ↓
[50文字未満] → 依存関係ファイルのパーシング + ドメイン検知を試行
              ├─ シグナルあり → 最小プロフィール生成
              └─ シグナルなし → "詳細分析不可"と正直に表示
```

**原則:** 存在しない情報を作り出しません。 情報が不足している場合は、不足していると表示します。

## 9. 技術スタック

| 区分 | 技術 |
|---|---|
| 言語 | Python |
| GitHubデータ収集 | aiohttp + asyncio (非同期) |
| 埋め込みモデル | jhgan/ko-sroberta-multitask |
| ベクトル検索 | FAISS (CPU) |
| 採用求人データ | Wanted 2,000件 + Jumpit 1,000件 + Remember 400件 |
| 年収データ | Jumpit・Wanted 2025 職務別・年次別中央値 |
| 環境 | RTX 4090, Windows, Docker, PyTorch |

### 外部APIの依存関係

**なし。** パイプライン全体がローカルで動作します。
GitHub API（データ収集）を除き、外部サービスの呼び出しはありません。

## 11. 実行方法

### 事前準備
1. `.env`ファイルに`Github_api_token`を設定
2. `pip install -r requirements.txt`を実行
3. `vector/`フォルダにFAISSインデックスファイルが存在することを確認

### 実行
```bash
# E2Eパイプライン (全体の流れ)
python run_git2value.py

# GitHub分析のみを単独実行
python github_extractor.py

# 年収バンド照会のみを単独テスト
python valuation_engine.py
```

`run_git2value.py`の`__main__`ブロックで`TARGET_USERNAME`、`TARGET_REPOS`、`APPLICANT_YEARS`を修正して分析対象を変更します。

## 12. キャプストーンデザイン戦略

### 発表構造

```text
1. 問題定義
   "新人開発者が自身のポートフォリオの市場競争力を把握できない"

2. 現場での検証
   現役の採用担当者へのインタビューを通じ、問題が実在することを確認
   (→ チームでインタビュー1〜2件の確保が必要)

3. 解決策
   技術アーキテクチャの説明 (FAISS、埋め込み、非同期クローリングなど)

4. 産業界との連携
   現役のフィードバックを診断基準に反映
   就活生5〜10名を対象とした実使用テストの結果

5. 結果および拡張性
```

### 必ず補完すべき項目

| 項目 | 方法 |
|---|---|
| **産業界との連携** | IT企業の採用担当者または開発チーム長へのインタビュー1〜2件 |
| **ユーザー検証** | 就活生5〜10名を対象とした実際のGitHub分析 → フィードバックの収集 |

### 今後の拡張（発表スライド1枚用）

| 拡張方向 | 説明 |
|---|---|
| B2B転換 | 同一のエンジンを採用担当者向けのスクリーニングツールとして提供 |
| リアルタイム求人連動 | 採用プラットフォームのAPI連携により、求人DBをリアルタイムで更新 |
| 経験者（中途）への拡張 | LinkedIn/履歴書との結合により、経験者の分析が可能 |

## 13. 既知の限界

このシステムが**できないこと**を明確に認識して使用する必要があります。

| 限界 | 理由 |
|---|---|
| GitHubを持たない応募者の分析は不可 | 入力データ自体が存在しないため |
| コード全体の品質判定は不可 | サンプルに基づく間接評価という本質的な限界があるため |
| 正確な年収予測は不可 | GitHubのスコアと年収の間の検証された相関関係が不在のため |
| GitHubを使用しない開発者はカバー不可 | 新人の中でもGitHubを積極的に管理している割合は一部に過ぎないため |
| 面接の合否予測は不可 | カルチャーフィット、面接でのパフォーマンスなど、GitHub以外の変数が存在するため |
