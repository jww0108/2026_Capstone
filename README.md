# Git2Value — GitHub Portfolio Diagnosis & Job Strategy Report

> 최종 갱신: 2026.05.11 | 스펙 버전: v6.3  
> 대상 독자: 팀원 전원 / 발표 준비 / 실행 테스트용

日本語版は [README_JAPAN.md](README_JAPAN.md) を参照してください.

## 1. 프로젝트 소개

> **신입 개발자를 위한 GitHub 포트폴리오 진단 & 취업 전략 리포트 서비스**

Git2Value는 지원자의 GitHub 레포지토리를 분석하여 다음 세 가지를 제공합니다.

1. 포트폴리오의 강점과 보완점
2. 신입 기준 직무 매칭 결과
3. 매칭 직무의 시장 연봉 밴드

이 시스템은 경력직 평가 도구가 아니라, **신입·취준생이 자신의 GitHub 포트폴리오를 객관적으로 점검하고 지원 방향을 잡기 위한 MVP**입니다.

---

## 2. 왜 신입 전용인가

| 구분 | 경력직 | 신입 / 취준생 |
|---|---|---|
| GitHub의 의미 | 전체 경력의 일부 | 사실상 핵심 코드 포트폴리오 |
| 평가 변수 | 회사 경력, 실무 경험, 협상력 등 | 프로젝트 품질, 기술 스택, 개발 활동 기록 |
| 연봉 예측 | GitHub만으로 판단 불가 | 시장 밴드 참고 수준 제공 가능 |
| 사용자 니즈 | 상대적으로 낮음 | 피드백과 방향성이 강하게 필요 |

Git2Value는 GitHub만으로 합격 여부나 정확한 연봉을 예측하지 않습니다. 대신 **포트폴리오 상태, 직무 방향성, 시장 참고선**을 함께 보여주는 데 초점을 둡니다.

## 3. 서비스 전체 흐름

```text
GitHub Username + 레포 URL 리스트 (최대 3개)
        ↓
GitHubExtractor
  - GitHub API 기반 레포 데이터 수집
  - README / 파일 구조 / 커밋 / 언어 / 프레임워크 분석
  - 팀·개인 레포 판정
  - GitHub 점수 산출
        ↓
Profile Builder
  - 레포 분석 결과를 채용공고 문체의 프로필 텍스트로 변환
  - 도메인 감지 결과와 기술 스택 결합
        ↓
FAISS Job Matching
  - 채용공고 벡터 DB와 유사도 검색
  - 신입 기준 경력직 공고 필터링
  - 도메인 일치 공고 리랭킹
        ↓
Final Report
  - 모듈 A: 포트폴리오 진단
  - 모듈 B: 직무 매칭
  - 모듈 C: 시장 연봉 밴드
```

## 4. 모듈 A — 포트폴리오 진단

### 4.1 하는 일

GitHub 레포지토리를 분석하여 레포별 진단, 종합 점수, 개선 가이드를 출력합니다.

분석 대상 레포는 최대 3개입니다.

```text
권장 입력 구조:
- 메인 프로젝트 1개
- 서브 프로젝트 1~2개
```

대표 프로젝트 중심으로 평가하기 위해, 너무 많은 레포를 한 번에 넣는 방식은 제한했습니다.

---

### 4.2 팀 / 개인 레포 판정

기존에는 지원자 본인 커밋만 기준으로 작성자 수를 계산하면 팀 프로젝트도 개인 레포로 오판될 수 있었습니다. 현재는 다음 기준을 분리해서 사용합니다.

```text
지원자 커밋 목록
→ 개발 활동량, 커밋 메시지, 작업 일관성 평가에 사용

레포 전체 커밋 목록
→ 팀/개인 판정, 전체 작성자 수, 협업 신호 계산에 사용
```

작성자가 2명 이상이면 팀 레포로 판정하며, `Fork` 여부는 팀/개인 판정과 분리하여 보조 정보로만 사용합니다.

예시:

```text
Ttakji_lab-mobile_development_dep [팀 레포 · 6명 협업]
JuicyMatch [개인 레포]
```

---

### 4.3 GitHub 점수 구조

GitHub 점수는 100점 만점이며, 세 축으로 나누어 산출합니다.

| 축 | 배점 | 의미 |
|---|---:|---|
| 개발 활동량 | 60점 | 유효 코드 변경량, 분석 가능한 커밋 수, 설정·데이터 기여 등을 기반으로 한 개발 활동 규모 |
| 프로젝트 관리도 | 30점 | 테스트 코드, CI/CD 구성, 개발 지속 기간 등 프로젝트 관리 신호 |
| 작업 일관성 | 10점 | 지원자 커밋 간격의 안정성과 작업 리듬 |

기존의 `기여도`라는 표현은 개인 프로젝트에서 오해를 만들 수 있어, 현재는 **개발 활동량**으로 표현합니다. 이는 팀 내 참여율이 아니라 GitHub상에 드러난 유효 코드 변경량과 커밋 활동량을 의미합니다.

---

### 4.4 여러 레포의 최종 점수

여러 레포를 입력한 경우 단순 평균이 아니라, 대표 프로젝트를 더 크게 반영합니다.

```text
최종 GitHub 점수 = 대표 프로젝트(최고점) 70% + 전체 레포 평균 30%
```

이 방식은 취준생 포트폴리오에서 보통 가장 완성도 높은 대표 프로젝트가 중요한 점을 반영합니다. 동시에 나머지 레포 상태도 30% 반영하여 전체 포트폴리오 관리 상태를 일부 반영합니다.

---

### 4.5 Fork 레포 보정

Fork 레포는 단순 복제나 점수 부풀리기 가능성이 있어 보수적으로 다룹니다. 다만 팀 프로젝트에서는 협업 편의, 권한 분리, OS 환경 차이 등으로 정상적으로 fork를 사용하는 경우가 많기 때문에, 현재는 fork 여부만으로 일괄 감산하지 않습니다.

보정 기준:

```text
Fork 아님
→ 감산 없음

Fork + 팀 레포
→ 팀 평균 활동 비율 이상이면 감산 없음
→ 팀 평균보다 낮으면 활동 비율에 따라 단계적 감산

Fork + 개인 레포
→ 본인 커밋 수와 유효 LOC가 충분하면 감산 완화
→ 단순 복제 가능성이 높으면 강하게 감산
```

이를 통해 오픈소스 복제나 점수 부풀리기는 방지하면서도, 실제 팀 프로젝트에서 발생하는 정상적인 fork 구조는 과하게 불이익을 받지 않도록 했습니다.

---

### 4.6 레포별 진단 항목

공통 평가 항목:

| 항목 | 설명 |
|---|---|
| README 품질 | 프로젝트 목적, 기술 스택, 실행 방법, 이미지/데모 포함 여부 |
| 프로젝트 구조 | 디렉터리 구성, `.gitignore`, 파일당 평균 LOC 등 |
| 커밋 메시지 | 무의미한 커밋 메시지 비율, Conventional Commits 적용 가능성 |

팀 레포 필수 점검 항목:

| 항목 | 설명 |
|---|---|
| 테스트 | 테스트 파일 또는 테스트 프레임워크 사용 여부 |
| CI/CD | GitHub Actions, Dockerfile, 빌드 자동화 신호 |
| 배포 | 배포 설정, 빌드 결과물, 서비스 링크, itch.io 등 |
| 커밋 리듬 | 지원자 기준 활성 주당 커밋 수와 협업 신호 |

개인 레포에서는 테스트, CI/CD, 배포, 커밋 리듬을 필수 감점 요소로 강하게 보지 않고, 팀 레포에서 더 중요한 협업·운영 신호로 평가합니다.

## 5. 모듈 B — 직무 매칭

### 5.1 하는 일

지원자의 GitHub 분석 결과를 채용공고 문체의 프로필 텍스트로 변환한 뒤, FAISS 벡터 검색을 통해 유사한 채용공고를 찾습니다.

```text
GitHub 분석 결과
→ 프로필 텍스트 변환
→ FAISS 유사도 검색
→ 신입 기준 경력직 필터링
→ 도메인 일치 리랭킹
→ 상위 공고 출력
```

---

### 5.2 프로필 변환 기준

도메인 감지와 기술 스택은 다음 우선순위로 반영됩니다.

| 우선순위 | 시그널 | 예시 |
|---|---|---|
| 1순위 | 파일명 / 폴더명 | `GameManager.cs`, `PlayerController.cs` → 게임 개발 |
| 2순위 | README 키워드 | Unity, Spring, React, FastAPI 등 |
| 3순위 | 의존성 파일 | `package.json`, `requirements.txt`, `build.gradle` 등 |
| 4순위 | 언어 통계 | C#, JavaScript, Python 등 |

언어만으로 직무를 판단하면 C# 게임 프로젝트가 일반 SW 개발로 오분류될 수 있으므로, 파일 구조와 도메인 신호를 함께 사용합니다.

---

### 5.3 신입 기준 경력직 필터링

Git2Value는 신입·취준생을 대상으로 하므로, 명확한 경력직 공고는 추천 후보에서 제외합니다.

제외 대상 예시:

```text
1~4년
3~5년
3년 이상
경력 개발자
경력직
시니어 / Senior
Experienced Engineer
3+ years
```

허용 대상 예시:

```text
신입
주니어
경력무관
신입/경력
경력 미기재 공고
```

단, 경력 조건이 명시되지 않은 공고는 신입 지원 가능성이 있다고 보고 후보에 남깁니다. 따라서 출력 결과는 “명시적 신입 공고”와 “경력 조건 미기재 공고”가 함께 포함될 수 있습니다.

## 6. 모듈 C — 시장 연봉 밴드

### 6.1 하는 일

매칭된 직무의 신입~3년 구간 시장 연봉 범위를 제공합니다.

중요한 원칙:

```text
GitHub 점수는 연봉 계산에 사용하지 않습니다.
```

연봉은 기술력만으로 결정되지 않고 회사 규모, 지역, 협상력, 포지션 상황에 따라 크게 달라지므로, Git2Value는 정확한 개인 연봉 예측이 아니라 **시장 참고 밴드**만 제공합니다.

---

### 6.2 데이터 기준

- 점핏 2025 채용공고 기반 직무별 연봉 데이터
- 원티드 2025 채용공고 기반 직무별 연봉 데이터
- 직무별 신입~3년 구간 중앙값과 현실 분포 범위

출력 예시:

```text
매칭 직무       : 게임 클라이언트
구간            : 신입 (0~3년)
시장 중앙값     : 약 3,554만원
실제 분포       : 3,021만 ~ 4,265만원
```

참고 직무는 매칭 공고와 감지 도메인을 기준으로 별도 출력합니다.

## 9. 실행 방법

### 9.1 의존성 설치

```bash
pip install -r requirements.txt
```

### 9.2 `.env` 설정

프로젝트 루트에 `.env` 파일을 만들고 GitHub API 토큰을 입력합니다.

```text
Github_api_token=your_github_token_here
```

`.env` 파일은 절대 GitHub에 올리지 않습니다.

### 9.3 필수 데이터 확인

아래 파일이 있어야 전체 파이프라인이 실행됩니다.

```text
vector/git2value_faiss.index
vector/git2value_metadata.json
data/jumpit_data/
data/wanted_data/
```

### 9.4 실행

`run_git2value.py` 하단의 입력값을 수정합니다.

```python
TARGET_USERNAME = "github_username"
TARGET_REPOS = [
    "owner/repository/tree/branch"
]
APPLICANT_YEARS = 0
```

실행:

```bash
python run_git2value.py
```

경력 필터 정규식 변경 후 결과가 이상하면 캐시를 삭제하고 다시 실행합니다.

```bash
del vector\experience_cache.json
python run_git2value.py
```

## 11. 알려진 한계

| 한계 | 설명 |
|---|---|
| GitHub 없는 지원자 분석 불가 | 입력 데이터가 없으면 분석할 수 없음 |
| 코드 전체 품질 판단 불가 | 전체 소스 코드를 정적으로 완전 분석하는 시스템은 아님 |
| README 의미 분석 한계 | 룰베이스 기반이라 문서의 깊이를 완벽히 판단하지 못함 |
| 경력 필터 한계 | 정규식 기반이라 특이한 공고 표현은 놓칠 수 있음 |
| 직무 매칭 한계 | 채용공고 데이터셋 커버리지에 따라 결과가 달라질 수 있음 |
| 정확한 연봉 예측 불가 | 연봉은 회사, 지역, 협상력에 따라 달라짐 |
| 면접 합격 예측 불가 | 컬처핏, 면접 역량 등 GitHub 밖 변수를 반영할 수 없음 |

## 12. 향후 개선 방향
